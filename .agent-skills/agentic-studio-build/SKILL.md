# Agentic Studio Build

Use this skill for reusable client-build workflows where several agents or project phases share one repository and delivery record.

## Discovery gate

Before editing, identify the client, audience, repository, branch, current stack, live route, approved visual system, locked content, providers, credentials boundary, deployment path, and owner approval state.

Read the project handover, issue board, current source, and any approved brand or content references. Separate confirmed decisions, recommendations, placeholders, and open questions.

## Preserve the current layer

Keep the existing stack until the owner approves a migration. Extend the current implementation with native patterns. Treat a future framework as a separate phase with a written architecture handoff and a review checkpoint.

Avoid mixing framework files into a static site. Keep provider integrations proportionate to the current layer. Use placeholders for owner-supplied URLs, keys, account IDs, and schedules.

## Stage the work

1. **Baseline:** inspect and record the current source, live behaviour, visual system, content, and risks.
2. **Review build:** make the smallest useful change with reversible source edits.
3. **Validation:** run content, link, accessibility, responsive, form, and visual checks.
4. **Owner review:** record decisions and open items before merge or publication.
5. **Connected systems:** introduce CRM, database, hosting services, project operations, and automation through an explicit architecture phase.
6. **Handover:** leave a concise Markdown record and one clear next action.

## Provider integration pattern

For each integration, record the provider, account owner, purpose, data fields, URL or key status, privacy considerations, test method, fallback path, and phase. Keep secrets out of source. Keep forms and booking journeys usable before provider automation is complete.

## Language and audience

Choose the audience and language variant before writing. Use UK English for UK and South African audiences. Use US English for US audiences. Use plain, specific, affirmative sentences.

Describe the offer, function, value, requirements, and next step. Avoid generic AI or agency language, inflated claims, invented evidence, negative comparisons, exclusion-led copy, and long em dashes. Avoid `not`, `real`, `actual`, and `human` unless a precise technical or role-specific context requires them. Use roles such as agent, developer, orchestrator, owner, user, and person. Describe AI as a tool that extends capability.

## Visual preservation

Treat approved colour tokens, typography, layout, spacing, component patterns, interaction states, and content as locked. Add new material through existing design tokens and components. Check desktop, mobile, focus, loading, error, reduced-motion, and reduced-transparency states where relevant.

## Handover format

Use a Markdown handover containing:

- task and owner outcome;
- repository, branch, environment, and checkpoint;
- source and issue references inspected;
- confirmed decisions and assumptions;
- completed files and changes;
- validation results;
- open decisions and required owner inputs;
- deployment state;
- one next action;
- commit and issue references.

Use GitHub Issues as the coordination board. Write one concise issue update per meaningful batch. Keep presentation outlines as optional planning notes. Create a deck only when the owner requests one.

## Delivery gate

Before merge or publication, confirm that the intended layer remains intact, locked decisions remain preserved, new copy follows the audience rules, links and forms work, accessibility checks pass or have recorded findings, credentials remain protected, and owner approval is recorded.
