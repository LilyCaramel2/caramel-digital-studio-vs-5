# Agentic Studio Build

Use this skill for reusable client-build workflows where several agents or project phases share one repository and delivery record.

When a project contains `AGENT_LANGUAGE_PROTOCOL.md`, load it as the shared baseline for agent communication, public copy, client replies, invoices, forms, chatbots, translations, and handovers. When `CARAMEL_WRITING_AUDIT_AGENTIC.md` exists, apply its purpose, meaning, voice, language, and delivery passes. Apply client-specific voice rules after the shared baseline and keep each domain’s identity separate.

## Discovery gate

Before editing, identify the client, audience, repository, branch, current stack, live route, approved visual system, locked content, providers, credentials boundary, deployment path, and owner approval state.

Read the project handover, issue board, current source, and any approved brand or content references. Separate confirmed decisions, recommendations, placeholders, and open questions.

## Preserve the current layer

Keep the existing stack until the owner approves a migration. Extend the current implementation with native patterns. Treat a future framework as a separate phase with a written architecture handoff and a review checkpoint.

For every website, build the static HTML, CSS, Tailwind, and JavaScript version first. Complete review and owner approval before moving that approved site to Next.js. Keep application, CRM, database, hosting, project-operations, and chatbot work in the later connected-systems phase.

When a migration is on hold, keep the current layer healthy and deliver approved static improvements, QA, documentation, and handovers before resuming connected systems.

Avoid mixing framework files into a static site. Keep provider integrations proportionate to the current layer. Use placeholders for owner-supplied URLs, keys, account IDs, and schedules.

Prefer local open-source models and deterministic tools. Use free tiers where they meet the task. Require explicit owner approval before paid APIs or unnecessary hosted processing. Protect source, prompts, client records, and intellectual property. Conserve tokens with bounded batches, concise Markdown handovers, local references, cached research, and file-based transfer.

Use Google Workspace as the default low-cost coordination and file layer when client Gmail or free Workspace access is available. Use Gemini or Gemma where approved. Keep PDFs, media, research, and handovers in the owner-approved C-drive silo or approved Google-backed storage. Let Linear, Render, Supabase, GitHub Issues, and similar systems reference those files through controlled links. Record ownership, access, privacy, retention, and link status.

At migration time, verify the latest stable Next.js release and official Vercel guidance. Select the supported release that fits the project; keep the framework version as a dated decision rather than treating an older minor version as permanent.

## Stage the work

1. **Baseline:** inspect and record the current source, live behaviour, visual system, content, and risks.
2. **Review build:** make the smallest useful change with reversible source edits.
3. **Validation:** run content, link, accessibility, responsive, form, and visual checks.
4. **Owner review:** record decisions and open items before merge or publication.
5. **Connected systems:** introduce CRM, database, hosting services, project operations, and automation through an explicit architecture phase.
6. **Handover:** leave a concise Markdown record and one clear next action.

## Provider integration pattern

For each integration, record the provider, account owner, purpose, data fields, URL or key status, privacy considerations, test method, fallback path, and phase. Keep secrets out of source. Keep forms and booking journeys usable before provider automation is complete.

For a static Web3Forms integration, inspect the existing form marker, hidden access-key field, JavaScript submission handler, status element, success state, error state, and direct-contact fallback before adding a second form. Reuse the established field names and provider route. Keep any active browser-side provider key confined to the approved project source and keep review drafts on placeholders.

For a manual payment route, document the payment method, owner receipt check, confirmation sequence, private-data boundary, client email templates, and full booking-flow test. Test enquiry, payment instruction, payment confirmation, calendar invitation, meeting link, reminder, rescheduling, and cancellation as separate states.

Let the client choose from the owner-approved payment menu. Record country, preferred method, selected route, amount, receipt reference, and confirmation state. Keep optional referral links as owner-supplied placeholders until the owner provides the final URL. Keep launch-phase payment decisions separate from future provider discovery.

When a repository has an operations guide and named payment handovers, read the operations guide first and follow its file map. Preserve the distinction between client-facing instructions, private templates, simulations, test checklists, and future automation tasks.

## Language and audience

Choose the audience and language variant before writing. Use UK English for UK and South African audiences. Use US English for US audiences. Use plain, specific, affirmative sentences.

Describe the offer, function, value, requirements, and next step. Avoid generic AI or agency language, inflated claims, invented evidence, negative comparisons, exclusion-led copy, and long em dashes. Avoid `not`, `real`, `actual`, and `human` unless a precise technical or role-specific context requires them. Use roles such as agent, developer, orchestrator, owner, user, and person. Describe AI as a tool that extends capability.

## Visual preservation

Treat approved colour tokens, typography, layout, spacing, component patterns, interaction states, and content as locked. Add new material through existing design tokens and components. Check desktop, mobile, focus, loading, error, reduced-motion, and reduced-transparency states where relevant.

## Handover format

Use a Markdown handover containing:

- task and owner outcome;
- repository, branch, environment, and checkpoint;
- source and issue references inspected;
- confirmed decisions and assumptions;
- completed files and changes;
- validation results;
- open decisions and required owner inputs;
- deployment state;
- one next action;
- commit and issue references.

Create the handover at task start with the baseline state and intended scope. Keep adding findings, decisions, changed files, checks, and open items during the task. Finish with one clear continuation action so a later agent can resume after a context limit, token interruption, or handoff.

Use GitHub Issues as the coordination board. Write one concise issue update per meaningful batch. Use Markdown handovers and checklists for agent coordination. Use presentation slides only when the owner explicitly requests a client pitch or presentation.

## Delivery gate

Before merge or publication, confirm that the intended layer remains intact, locked decisions remain preserved, new copy follows the audience rules, links and forms work, accessibility checks pass or have recorded findings, credentials remain protected, and owner approval is recorded.

Always leave the completed handover and coordination update, including for review builds and partial implementation batches.
